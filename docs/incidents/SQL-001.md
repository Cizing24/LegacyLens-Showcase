# SQL-001 — 歷史案件量增加後的條件查詢成本

分類：Public Dataset Observation + 受控效能實驗；沒有虛構企業效益或事故。

## 問題、影響與初始假說

Baseline `(@status='' OR c.Status=@status)` 與 optional title predicate 讓查詢簡短，但沒有適合條件／排序的 covering index。100k 311 資料的實測 Baseline P50 22.342 ms、3,255 Logical Reads；這是本機回應，並非宣稱使用者已感到 SLA 違約。調查假說是 optional predicate 與排序存取路徑導致掃描，並非先假定需要新架構。

## 調查與決策

先以官方字典與 allowlist 匯入真實 311 子集，再收集三個資料規模、三個方案的 actual execution plan / IO / repeated latency。只改寫 SQL 的 reads 沒有變少，故單靠程式重構不足。加 covering index 後讀取降低且結果等價，選擇小範圍 predicate 改寫與索引。

應用只從固定條件片段組合 SQL，所有值仍有明確型別參數；沒有插入使用者輸入到 SQL 字串。比較 keyset pagination 可降低深頁成本，但會改變頁碼契約，本次保留 OFFSET；Full Text Search 也超過目前分類主旨 substring 檢索需求。

## 實作與驗證

CaseStore.Search、migration 002、SearchTests、資料工具與 Benchmark。保留舊 SQL 作為可執行 comparison。全部數據、方法、trade-offs、資料規模與剩餘風險見 [RESULTS](../benchmarks/RESULTS.md)，來源／授權見 [PROVENANCE](../datasets/PROVENANCE.md)。

100k indexed P50 1.0832 ms、P95 1.3413 ms、Logical Reads 87。原始 sample 各有 40 筆，5 次 warmup；三個 offset 結果一致。沒有 cold cache、跨機、production SQL instance、寫入成本或大量 concurrent users 的定量證據。
